# Short-lived AWS identity for the local refresh runner

## Decision

Use the AWS CLI's browser-based `aws login` flow as the local Mac's source
identity, then assume a dedicated `takonbini-refresh-runtime` IAM role through a
named `takonbini-refresh` profile. Run the refresh with only
`AWS_PROFILE=takonbini-refresh` and `AWS_REGION=ap-northeast-1`; do not put AWS
access keys or session tokens in the Takonbini environment file.

This fits the established account better than introducing IAM Identity Center
solely for this hobby workload. The baseline already confirms that local sign-in
is enabled, MFA is in use, and the human administrator has no access keys. It
also records that the previous scraper access key was deleted and that routine
runtime access should not inherit the human administrator's broad permissions
([repository baseline](../evidence/phase-0-baseline-and-rollback.md#human-aws-administrator),
[legacy scraper identity](../evidence/phase-0-baseline-and-rollback.md#legacy-scraper-identity)).

AWS documents `aws login` as a browser flow that produces temporary credentials,
automatically refreshes them for up to 12 hours, and works with AWS SDKs. It
requires AWS CLI 2.32.0 or newer and the `SignInLocalDevelopmentAccess` managed
policy on the source identity. If the account later adopts IAM Identity Center,
replace only the source profile: AWS recommends IAM Identity Center's automatic
credential refresh for that case. The runtime role and application do not need
to change ([AWS CLI local sign-in](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-sign-in.html),
[IAM Identity Center credentials](https://docs.aws.amazon.com/singlesignon/latest/userguide/howtogetcredentials.html)).

The local setup should have two profiles:

```ini
[profile takonbini-login]
login_session = takonbini
region = ap-northeast-1

[profile takonbini-refresh]
role_arn = arn:aws:iam::<account-id>:role/takonbini-refresh-runtime
source_profile = takonbini-login
role_session_name = local-refresh
region = ap-northeast-1
```

The exact `login_session` stanza is generated by `aws login`; it should not be
hand-authored from this example. AWS CLI role profiles use the source profile to
call STS `AssumeRole` and then use the role's temporary credentials for commands.
The source principal needs only `sts:AssumeRole` on this one runtime role, and
the role trust policy should name only that source principal
([AWS CLI role profiles](https://docs.aws.amazon.com/cli/latest/userguide/cli-configure-role.html)).

The preflight is:

1. `aws login --profile takonbini-login` when the cached browser session is not
   valid.
2. `AWS_PROFILE=takonbini-refresh aws sts get-caller-identity` and require the
   returned ARN to be an assumed session of `takonbini-refresh-runtime`.
3. Check the configured region is exactly `ap-northeast-1`.
4. Call the read-only resource checks listed below before starting the runner.

`sts:GetCallerIdentity` requires no allow permission, even if an identity policy
explicitly denies it, so it does not need to appear in the runtime policy
([STS API reference](https://docs.aws.amazon.com/STS/latest/APIReference/API_GetCallerIdentity.html)).

## Permission boundary

Terraform should create one customer-managed **data-plane policy** and attach it
to the local `takonbini-refresh-runtime` role. It should contain no IAM,
Terraform/backend, billing, DynamoDB table-management, or search
control-plane permissions.

| Capability | Allowed actions | Resource boundary |
| --- | --- | --- |
| DynamoDB preflight | `dynamodb:DescribeTable`, `dynamodb:DescribeTimeToLive` | Only the new Takonbini runtime table ARN(s) |
| Workflow/catalog reads | `dynamodb:GetItem`, `dynamodb:BatchGetItem`, `dynamodb:Query` | Only those table ARN(s) and their explicit index ARN(s) |
| Workflow/catalog writes | `dynamodb:PutItem`, `dynamodb:UpdateItem`, `dynamodb:DeleteItem`, `dynamodb:BatchWriteItem`, `dynamodb:TransactWriteItems` | Only those table ARN(s); index ARNs only for `Query` |
| Search preflight and writes | Provider-specific minimum described below | Only the selected Takonbini projection resource and generation namespace |

Do not grant `dynamodb:Scan` by default. The clean-sheet access-pattern design
must make every normal runner operation addressable by key or index. Add Scan
only if a later decision identifies a bounded administrative recovery path, and
put that permission on a separate operator role rather than the unattended
runtime role. Likewise, the runner does not need `CreateTable`, `UpdateTable`,
`DeleteTable`, TTL configuration, backup, restore, tagging, IAM, or KMS
administration; Terraform owns infrastructure changes.

The final policy must use the concrete table and index ARNs selected by the data
model. `TransactWriteItems` is required because DynamoDB transactions provide
the atomic multi-item write primitive needed for lease/publication invariants;
AWS applies the transaction atomically or rejects it as a whole
([DynamoDB `TransactWriteItems`](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_TransactWriteItems.html)).

### Search is an additive policy fragment

The search-provider ticket is still open, so identity design must not pre-grant
an assumed provider. Terraform should attach a separate search policy fragment
only after that decision:

- For an S3-hosted static projection, allow `s3:GetBucketLocation` and a
  prefix-scoped `s3:ListBucket` for preflight, plus `s3:GetObject`,
  `s3:PutObject`, and `s3:DeleteObject` only under the Takonbini projection
  prefix. Do not grant bucket-policy, lifecycle, ACL, or bucket-management
  actions.
- If OpenSearch Serverless survives the sub-RM1 decision, the IAM role needs
  `aoss:APIAccessAll` on only the chosen collection ARN, while a separate data
  access policy names the role and limits it to the generation index pattern
  with only the required index/document permissions. OpenSearch Serverless
  deliberately separates IAM data-plane access from its data access policy;
  the runner needs neither Dashboards access nor collection/security-policy
  administration
  ([OpenSearch Serverless data access](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-data-access.html),
  [supported operations](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-genref.html)).
- For any other provider, grant only its chosen AWS resource access. A
  third-party API token remains outside IAM and must not be stored in the AWS
  profile.

Keep the projection namespace generation-scoped. The role may build, validate,
and delete its own candidate generation, but the final IAM shape should be
revisited after the publication protocol decides whether advancing the active
pointer belongs to this writer or to a narrower publisher role.

## Transition to ECS/Fargate

Application code must instantiate AWS SDK clients without explicit credentials.
AWS SDK default credential chains can refresh standardized temporary
credentials without application code, and include both shared profile and ECS
container providers
([AWS SDK credential provider chain](https://docs.aws.amazon.com/sdkref/latest/guide/standardized-credentials.html),
[container credential provider](https://docs.aws.amazon.com/sdkref/latest/guide/feature-container-credentials.html)).

For the later compute migration:

1. Create `takonbini-refresh-task` with an ECS task-role trust policy.
2. Attach the same customer-managed data-plane policy used by the local runtime
   role, plus the selected search fragment.
3. Set that role as the task role. Do not set `AWS_PROFILE` or credential
   environment variables in ECS; the SDK obtains automatically rotated task
   credentials from the container provider.
4. Keep the ECS **task execution role** separate. It is for the ECS agent's
   image-pull/logging/secret-delivery work, not the application's DynamoDB or
   search calls.
5. Remove the local role and source `sts:AssumeRole` grant when local execution
   is retired.

AWS explicitly distinguishes application permissions on the task role from
agent permissions on the task execution role and recommends a task role for
credential isolation and auditability
([ECS task IAM role](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-iam-roles.html),
[ECS role best practices](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/security-iam-roles.html)).

## Verification gates

Before a credentialed refresh is allowed:

- confirm no `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, or
  `AWS_SESSION_TOKEN` is present in the runner's persisted environment file;
- confirm `get-caller-identity` resolves to the dedicated runtime role, never
  the administrator identity;
- prove all required DynamoDB and chosen search preflight/read/write calls in a
  disposable candidate generation;
- prove representative denied calls: IAM enumeration, DynamoDB table mutation,
  unrelated table access, unrelated search namespace access, and search
  control-plane mutation;
- validate the Terraform IAM policy with IAM Access Analyzer, then use observed
  CloudTrail activity to remove unused actions after rehearsal. AWS recommends
  temporary role credentials, least privilege, and Access Analyzer policy
  validation/activity-based refinement
  ([IAM security best practices](https://docs.aws.amazon.com/IAM/latest/UserGuide/best-practices.html),
  [IAM Access Analyzer](https://docs.aws.amazon.com/IAM/latest/UserGuide/what-is-access-analyzer.html)).

This decision intentionally leaves concrete ARNs and the search fragment open
until the DynamoDB table model and sub-RM1 search architecture are selected. It
does settle the identity seam: short-lived human login, one assumable local
runtime role, provider-minimal data-plane access, no static keys, and a
credential-provider-neutral application that moves unchanged to an ECS task
role.
